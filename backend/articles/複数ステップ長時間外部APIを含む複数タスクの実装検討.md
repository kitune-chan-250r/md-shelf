# エグゼクティブサマリ

新規「処理A」は3～10の直列ステップを含む長時間ワークフローであるため、**非同期キュー駆動型**または**ワークフローオーケストレーション**による設計が適切です。具体的には、クライアントからのリクエスト受信時に即時にジョブIDを返却し、バックグラウンドで処理を進めます。候補としては、Spring Boot内でジョブテーブルを使って自前管理する方法、Amazon SQS＋ECS/EKSワーカー、あるいはAWS Step FunctionsとLambda（またはDurable Functions）によるサーバーレスワークフローがあります。  

推奨案としては、既存スタックとの親和性と可搬性を考慮し、Spring Bootアプリケーション（ECS/EKSまたはEC2）上で**SQSキュー+Spring Cloud AWSリスナー**方式を採用します。これによりRDBでジョブ状態を永続化しつつメッセージキューでタスクを分散でき、各ステップごとの再試行やデッドレター処理もSQS機能で容易に実装可能です。同時並列数はSQSとワーカー数で制御し、ジョブ完了後に結果状態をDB/Redisで管理します。**Step Functions**は可視化・耐障害性に優れますが、新たな学習コスト・費用増が懸念され、今回の既存Spring Boot環境への統合にはやや不向きです。  

本設計では、Spring Boot + PostgreSQL + Redis環境に最小限の影響で新機能を追加するため、SQSキューを介したワーカー設計とDB/Redisによるジョブ状態管理を軸とし、リトライ/タイムアウト/ロック等もSpring固有機能（@AsyncやSpring Retry、Redisson等）で実装します。AWS運用ではSQS/SNS/Step Functions/ECS/Lambda/RDS/ElastiCacheを比較し、コスト・運用面のトレードオフを表形式で示します。またフェイルオーバー対策としてDBまたはキュー方式でのジョブ再開パターンを複数案提示し、監視・テスト・セキュリティ・監査ログにも留意します。

## アーキテクチャ選択肢と比較

- **Spring内完結型（DBスレッド運用）**  
  - *概要*: リクエスト受信時にDB（PostgreSQL）にジョブレコードを登録し、Springのスレッドプールや`@Async`/スケジューラでジョブを定期ポーリングして処理。  
  - *利点*: 既存コード（Spring Boot）で完結するため学習コストが低い。トランザクション管理しやすい。  
  - *欠点*: サーバー障害でインメモリ処理が消失しやすい（耐障害性低い）。水平スケール時にジョブ重複実行を防ぐ必要あり（分散ロックが必須）。リクエスト応答はすぐ返せるが、長時間処理はサーバ負荷になる。  

- **メッセージキュー＋ワーカー方式（SQS＋Spring Cloud AWS + ECS/EKS）**  
  - *概要*: リクエスト時にSQSキューへメッセージを送信し、Spring Cloud AWSの`@SqsListener`や`MessageListenerContainer`でワーカーがメッセージを受信してステップ実行。各ステップ完了後に次ステップ用メッセージを再度SQSに送るか、状態テーブルを更新。  
  - *利点*: SQSはメッセージ永続化・多重配信防止（可視性タイムアウト）など耐久性・信頼性が高い。ワーカーは自動スケール可能で、サーバ障害時もメッセージはキューに残るため再実行できる。Spring Cloud AWSを使えばSpringらしい実装が可能。DLQによる失敗隔離、IAM/暗号化などAWSセキュリティ機能の恩恵も得られる。  
  - *欠点*: メッセージごとにキュー送受信コスト（$0.40/百万リクエスト程度）が発生。ステップ間のデータ受け渡しはメッセージペイロードやDBなどで実装する必要がある。標準キューは順序保証が弱い（順序を要する場合はFIFOキューにする必要）。コード複雑度は高め。  

- **AWS Step Functions + Lambda**  
  - *概要*: Step Functionsでステップワークフローを定義し、各ステップをLambda関数で実装。Step FunctionsはState Machineで順次実行・リトライ・エラーハンドリングを管理する。  
  - *利点*: ワークフローの可視化・管理が容易で、自動リトライ・並列分岐などビルトインで実現。状態と進捗はAWS側で管理され、サーバ管理不要（フルマネージド）。Durable Functions機能で最大1年まで実行可能。AWSサービスとの親和性（Lambda実行）も高い。  
  - *欠点*: 既存Springアプリと異なる実装になるため大幅なリファクタが必要。Lambdaの制限（最大15分/最大10GBメモリ）に注意（外部API90秒以内なら問題ないが、Javaへの対応が必要）。Step Functionsは利用料が`状態遷移数 x $0.000025`（東京だと1万件辺り約$0.25）と発生する。複雑な処理だとコスト増やプロキシ実装が煩雑に。  

- **AWS Lambda Durable Functions**  
  - *概要*: Lambda上でDurable Execution SDKを使い、1つのラムダ関数内でステップ呼び出しと待機をプログラム的に記述する。チェックポイント方式で再開可能。  
  - *利点*: Step Functions同様に状態管理やリトライを自動化でき、最大1年実行可能。コードは順次構造のまま記述でき、別のオーケストレータ不要。完全サーバレスで運用管理不要。  
  - *欠点*: Java SDKはあるが学習コストは高く、現状Lambda上でJava Spring環境を再現する必要あり。既存Spring Bootとの統合が難しい。新規開発コストが大きい。  

以上を比較すると、**既存Spring Boot環境への影響を最小化**しつつ耐障害性と拡張性を確保するため、**SQS＋Springワーカー方式**が現実的です。ステップごとの順次実行・リトライはSpring（or Step Functions連携）で実装し、サーバ障害時にはSQS＋DBでジョブ再開可能にします。Step FunctionsやDurable Functionsは興味深い選択肢ですが、既存資産を活かす観点からは重点度を抑えます。

## 詳細設計

### ジョブ管理とデータモデル
- **ジョブテーブル（PostgreSQL）**  
  - 列: `job_id (PK)`, `status`, `current_step`, `retry_count`, `payload (JSONB)`, `result (JSONB)`, `created_at`, `updated_at` など。  
  - `status`: NEW→IN_PROGRESS→STEPn_IN_PROGRESS/STEPn_DONE→COMPLETED/FAILED。処理フェーズを記録し、フェイルオーバー時に未完了ジョブを検出。  
  - `current_step`: 現在処理中のステップ番号。  
  - `retry_count`: 失敗リトライ回数管理。  
  - **考慮**: JPAエンティティに楽観ロック（バージョン番号）を設定し、同一ジョブの同時処理を防止。ジョブ受信時にサーバ間排他制御が必要な場合はこのテーブル上でSELECT…FOR UPDATEを用いるか、Redissonによる分散ロックを利用。  
- **ステップ成果物（オプション）**  
  - 必要に応じて、各ステップの結果を個別テーブルやRedisにキャッシュする。特に外部API応答が複数ステップで再利用される場合、Redisキャッシュに保存するとスループット向上可能。  
- **Redis（ElastiCache）**  
  - 分散ロック用: Redissonの `RLock` でジョブIDやステップごとにロックを取得。  
  - 処理キャッシュ: 外部APIの結果や一時的データをTTL付きでキャッシュ。  
  - メトリクスやキュー管理: レートリミットやバッファリング、参照用など。

### コード構成とSpring実装パターン例
- **新規Service層**: `ProcessingAService` に処理フローのステップメソッド群を実装。各メソッドはステップ固有処理（DB更新・外部API呼出し）を実行し、終了時に次ステップに移行するよう制御。全体ワークフローは `while` やState Patternで順次実行。  
- **メッセージリスナー**: Spring Cloud AWS の `@SqsListener` を使い、SQSキューをポーリング。メッセージ（例：`jobId`）受信時にWorker処理をトリガー。  
- **非同期実行（@Async）**: 長時間ステップ（外部API呼出し）をブロックせず実行するために、Springの `@Async` を併用。メソッドを `@Async` とし、`CompletableFuture` を返してバックグラウンドで動作させる。同時実行数は `Executor` のthread pool設定で制御。  
- **リトライ/タイムアウト**: Spring Retryでメソッドを `@Retryable(backoff=@Backoff(...))` とし、一時的エラー時に自動リトライ。リトライ回数上限とバックオフ時間は設定ファイル化し、エラー時は `@Recover` で障害ロジック（DLQ登録など）を実行。HTTPクライアントはタイムアウト設定（接続/読み取り 90秒以上）を行い、過大な待機は中断できるようにする。  
- **分散ロック/排他制御**: 同一ジョブIDの重複実行防止に、ジョブを取得するときにRedisロック（`RLock.tryLock()`）やDB行ロック（`SELECT ... FOR UPDATE`）を使用。Redissonのロックでは、数秒でロック自動破棄されるTTL付き鍵を使い、サーバクラッシュ時のデッドロック回避。  
- **デッドレター処理**: SQSのDLQ機能を活用し、指定回数失敗したメッセージを自動で別キューへ退避。Spring側では、DLQの新メッセージ用リスナーを別途実装し、手動リトライや障害解析を行う。DB方式なら失敗時に `status=FAILED` とし、調査後に再実行フラグで再登録する。

### 再試行・タイムアウト・回復戦略
- **ステップごと再試行**: Spring Retryで例外発生時に自動リトライ（最大3回程度）。90秒超えなど明確にタイムアウトした場合は `TimeoutException` としてリトライ処理。リトライ中もDB上では `current_step` は変えず、`retry_count` をインクリメント。再試行上限超過時は `EXHAUSTED` 例外を捕捉し、ステータスを失敗(`FAILED`)に設定。  
- **タイムアウト検知**: 外部API呼出しには専用のタイムアウト設定を付与。Springの `WebClient`/`RestTemplate`ではコネクト／リードタイムアウトを90秒に設定。タイムアウト時は `ResourceAccessException` 等を拾い、リトライまたはフェイル処理を行う。  
- **ワーカー再起動時の回復**: ジョブテーブルに未完了（`IN_PROGRESS`）のレコードが残っている場合、サーバ起動時や定期バッチで再度キューに投入して再開。DBをキーとしたオプティミスティック・ロックやRedisロックで二重投入を防止する。たとえば、ステータスが「STEPn_IN_PROGRESS」のまま滞留する場合は、一定時間後に「再投入」フラグを立てて別キューに送るロジックを用意。  
- **フェイルオーバーパターン比較**:  
  - *DB中心型*: 各ステップ完了後にDB更新し、サーバ落ち→復旧時にDBから継続可能。確実だが実装量増。  
  - *メッセージ中心型*: 各ステップ終了で次ステップ用メッセージをSQSにPUTし、障害時は未処理メッセージから再実行。単純だがメッセージ設計が複雑。  
  - *Step Functions*: AWS管理のため自動フェイルオーバー。   
  - トレードオフ: DB管理は移行負荷が小さく既存資産活用可能だが開発コストが大きい。SQS利用は可用性・スケーラビリティに優れるが運用管理(監視/アラート)が増える。

### 監視・メトリクス
- **メトリクス収集**: Spring Boot Actuator + Micrometerでアプリ内部メトリクスを取得し、Prometheus/Grafanaなどで可視化。AWSなら CloudWatchメトリクス（SQSキュー長、Lambda実行時間、RDS CPU/コネクション数等）を活用。例：キューの未処理メッセージ数、ジョブ完了数、処理時間分布、エラー率などを監視。  
- **ログ監視**: リクエスト受付→各ステップ→終了まで一連のログにJobIDを付与し、一貫して追跡可能にする。CloudWatch LogsやELKで集約し、異常アラートを設定。例：特定ステップのエラーが増加したらSlack通知。  
- **アラート設定**: SQSメッセージ長やRDS接続数が閾値を超えた場合、Auto ScalingのトリガーやSNS通知を設定。  
- **監査ログ**: 監査目的で、各ジョブの重要な状態変化（開始/終了/障害理由）をDBテーブルとは別に記録しておく。また、AWS CloudTrailでLambda/ECS起動ログ、RDS監査ログ（拡張ログなど）も保持して証跡とする。

### 運用手順・テスト
- **運用手順**: バージョン管理下でデプロイ。ステージング環境で新機能を検証後、本番に段階的適用。SQS設定、DLQ設定、DBマイグレーションはCI/CDパイプラインで実施。  
- **テスト**:  
  - *単体テスト*: 各ステップメソッドの正常系/異常系テスト。Spring Retryやロック処理もモックで網羅。  
  - *結合テスト*: AWS SQSをローカルStackまたはテスト環境で動かし、メッセージ送受信とDB更新を検証。外部API呼出しはStubサーバーを利用。  
  - *負荷テスト*: JMeterやGatlingで同時リクエストを実行し、SQSキューイング速度とワーカースループットを確認。ELB+AutoScalingの設定調整。  
  - *シナリオテスト*: サーバ強制終了→再起動によるジョブ再開の検証。不正データ・異常終了時のデッドレター動作確認。  

### 分散ロック・排他制御
- **Redissonによるロック**: `RLock lock = redisson.getLock("jobLock:"+jobId)` のように、ジョブIDをキーとして取得。処理後は必ず `unlock()`。Redissonは内部でRedisキーを使い、分散環境でもJavaのLock感覚で同期可能。  
- **DBロック**: 楽観ロック（@Version）や悲観ロック（`SELECT FOR UPDATE`）で同一行への同時更新を防止。状態遷移の競合防止。  
- **ロック取得失敗時の挙動**: 取得できなかった場合はワーカーは他のジョブを処理するか待機させ、タイムアウトで再取得可能にする。

## フェイルオーバー設計・ジョブ再開

- **RDB永続型アプローチ**: 全ステップの進捗をDBに保持し、障害後はDB検索で未完了ジョブを再取得。トランザクションにより復旧処理を実装する。十分に制御すればデータ整合性は高いが、コード側実装負担大。  
- **メッセージキュー型アプローチ**: 各ステップ完了時に次ステップのメッセージをキューに投入することで、ワーカーはキューから仕事を取得。障害復旧後は未消費メッセージが自然に再処理される（可視性タイムアウト経過後）。ジョブごとにキューを分けるか、メッセージにステップ情報を含める方式で実装可能。  
- **Step Functions型アプローチ**: 実装したState Machineが自動で復旧を担保。ただしワークフローの再開はStep Functions管理下で行われ、コード側ではオーケストレーション不要。  

**採用案**としてはDB＋SQS併用。DBでジョブ単位の状態を完全永続化しつつ、キューでワーカ処理を分散する。これにより、インスタンス障害時もDBの状態から進捗を復元し、SQSのメッセージで再実行できる。並行実行時は`job_id`単位でRedissonロックまたはDBロックを用い、重複処理を防止します。

## 移行戦略・段階的導入

1. **並行実装**: 既存機能をそのまま残しつつ、新機能用の新エンドポイントまたはフラグを追加して非同期パスを実装。旧処理を変更せず段階切替。  
2. **検証環境でE2Eテスト**: ステージングで外部APIとのシミュレーション、SQS/DLQ動作などを検証。ジョブテーブルの移行・スキーマ追加は本番リリース前に実施。  
3. **Canaryリリース**: 本番で一部リクエストを新方式で処理し（リリーストグル）、動作安定性を確認。エラーや遅延がないか慎重にモニター。  
4. **フル切替え**: 問題なければ全リクエストを非同期パスへ。旧同期処理はフェーズアウト、段階的に廃止。  
5. **フォールバック準備**: 予期せぬ障害時は旧同期処理に戻せる仕組みを残す（切替スイッチ等）。  

## セキュリティ・スケーリング・テスト・監査ログ

- **セキュリティ**: AWSリソースは最小権限のIAMロールでアクセス制御。SQSキューに対するアクセス権限はキュー固有のポリシーで制限。機密情報（DBパスワード等）はAWS Secrets ManagerやParameter Storeで暗号化保管。外部API呼出しはTLS/SSL通信を必須とし、タイムアウト設定でDoS対策。  
- **スケーリング**: ECS/EKSはAuto Scaling設定でトラフィック増に対応。SQSはリクエスト増に自動対応。RDSは読み取りリプリカ、Redisはクラスタ構成でスケールアウト可能。ワーカープール（ThreadPoolTaskExecutor）は必要に応じてコア数・上限数を調整。  
- **テスト**: 前述の各層テストに加え、セキュリティテスト（ペネトレーションテスト）、フェイルオーバーテスト（強制障害復旧シナリオ）、チャージやコンプライアンス監査用ログ出力の検証を実施。  
- **監査ログ**: 重要操作（ジョブ受信、ステップ開始/完了、例外発生）は全てログに記録し、必要なら永続ストレージ（RDS監査ログ、CloudWatch Logs）で保持。操作履歴は調査時に参照可能とする。
